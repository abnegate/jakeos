# D-0339 · Decide how prefix installers become installed applications
- Status: proposed
- Task: WIN-033
- Surfaces: none
- Layer: none
- Spikes: none

- Revisit when: an accepted later Decision supersedes this one, or a spike shows the chosen option cannot meet a Gate that cites it

## Context
A Windows `setup.exe` writes files, registry keys and Start Menu links into a prefix; nothing tells the native launcher that an application now exists or tells history that an install happened (Q-041, §28, §49). This decision fixes how a prefix installer's result becomes a launcher-visible installed application with a stable identity key and a system-history event, before WIN-061 builds the flow; it sits on prefix management (WIN-040) and the launcher (APP-032).

## Options

### Option A · Treat the prefix as the application
Summary: The prefix itself is the installed application: one launcher entry per prefix, named by the installer's product name, launched into the prefix's default executable.
Consequences: Simple identity (the prefix) and a natural uninstall (delete the prefix). Suites that install several programs into one prefix appear as one entry, and the default executable must be guessed.
Evidence: none

### Option B · Scan Start Menu links after install
Summary: After the installer exits, the personality diffs the prefix's Start Menu and registers one launcher entry per new shortcut, with the shortcut path as identity key and the diff as the history event.
Consequences: Matches what Windows users see and handles suites. Installers that write no shortcuts produce nothing, shortcut targets are heuristics (launchers, uninstallers must be filtered), and the diff must run inside the D-0223 layer model (base layer plus overlay).
Evidence: none

### Option C · Require a native manifest wrapper
Summary: An installed Windows application must be wrapped in a native manifest (generated by the personality or provided by the store) that names its executables, icon and identity; unwrapped prefixes are visible only in the personality's own tool.
Consequences: Clean identity, a real Package for the store and for history, and the same grant model as native applications. Every ad-hoc install needs a wrapping step the user or a generator performs, so the first-run experience for a random `setup.exe` is worse.
Evidence: none

## Decision
Proposed. Not yet accepted.
